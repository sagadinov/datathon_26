# Ограничения и известные ошибки

Метрики на обучающем наборе (42 ролика: 22 с нарушением, 20 без; детекции и правила на CPU,
`eval/results/`, прогон v2.14, 18.10.2026 00:20):

| метрика | значение |
|---|---|
| recall по нарушениям (вердикт на видео) | 18 / 22 = 0.82 |
| ложные срабатывания на чистых роликах | 1 / 20 (X-14) |
| точность вердикта по всем роликам | 37 / 42 = 0.88 |
| таймкод в пределах ±3 с / ±5 с (для найденных) | 0.72 / 0.89, медиана |Δt| 1.5 с |
| тип совпал с нашей разметкой (для найденных) | 0.78 |
| время обработки, кэш детекций / без кэша | ~2 с / 40–110 с на ролик |

## Что не ловим (пропуски на обучающем наборе)

1. **T7 «Наличные вне зоны видимости» (X-1, X-2, X-44).** Купюры в руках у груди и уход рук под
   стол не различимы детектором объектов: класс `hand` срабатывает редко, пачка в руках 25×35 px
   переименовывается в `phone`/`cup`. Правило T7 без позы реализовано, но отключено (`T7_A`, `T7_B`
   в CFG) — давало ложные срабатывания на чистых роликах. Эксперимент с позой (RTMPose-m ONNX,
   Apache-2.0; `src/pipeline/pose.py`, `src/pipeline/rules_t7.py`, `scripts/selftest_pose.py`,
   зависимости в `requirements-pose.txt`) ловит только X-1 из четырёх и держится на окончании
   ролика сразу после ухода рук, поэтому в сервис не включён. Вид сзади (камера A): «руки в
   счётную машинку» и «руки на коленях» дают одинаковые ключевые точки (X-2 против чистого X-3);
   вид спереди (камера B): запястья видны всегда, нужна память «пачка против одной купюры» (X-44).
2. **T1 по лежащей на столе пачке — ловится сравнением с фоном стола.** Пачка купюр 12–25 px не
   детектируется ни в полном кадре, ни на кропе стола ×3 (`src/pipeline/roi.py`, выключен). Работает
   `src/pipeline/blob.py`: медианный фон стола за первые 10 с (боксы людей маскируются), разность в Lab
   с вычитанием локального среднего (компенсирует изменение экспозиции при уходе кассира), порог
   по MAD шума, компонента 40–600 px², стабильная ≥3 кадра. Так найдены X-4, X-26, X-38. Пропуск:
   предмет, положенный туда, где чистый стол ни разу не был виден (X-15 — сумка под сидящим кассиром;
   её ловит детектор). Blob — «новый предмет на столе», не «наличные»: чеки и карты тоже считаются,
   поэтому правило T1 требует ещё ухода кассира или входа следующего посетителя.
3. **T10 «Дверь не закрыта при входе» (X-33).** Тип введён по двум роликам; геометрия входа через дверь
   в 2D не разделяет «отпустил ручку» и «стоит у двери», ловится только X-32.
4. **Дубликат X-4/X-47.** Один файл с двумя метками (57 с и 68 с); второе событие относится к T7
   и не ловится, поэтому для X-47 таймкод и тип считаются ошибочными (−2 ролика в «таймкод ±3 с»).

## Ложные срабатывания

- **X-14 (142 с, чистый):** зелёная инкассаторская сумка на столе распознаётся как «стакан» (T6) на
  21–26 с; сидящий кассир с рукой в сейфе на 117 с даёт T3. В остальных 19 чистых роликах
  срабатываний нет.
- Риски на новых видео: `safe_door_open` на закрытом шкафу зависит от ракурса (решено относительным
  порогом к фону ролика, но при сейфе, открытом с первого кадра, смена состояния не наблюдается);
  экран ноутбука при включённом свете оценивается только по яркости верхней части бокса ноутбука;
  люди за стеклянной дверью отсекаются по линии пола, которая выводится из бокса двери.

## Условия применимости

- Одна касса, одна камера сверху, стол с ноутбуком и счётной машинкой в кадре. Зоны (стол, место
  кассира, сейф, дверь) выводятся из детекций автоматически, пиксельных констант нет; ролики под
  другим ракурсом в датасете (три положения камеры) обрабатываются одной конфигурацией.
- Лица не распознаются; «кассир» — наиболее частая сидячая позиция у ноутбука за ролик, остальные
  люди — посетители. Если кассир отсутствует весь ролик, роли не назначаются.
- Без GPU VLM-подтверждение пропускается, описания формируются по шаблонам из видимых признаков.
- Бюджет 170 с на видео соблюдается за счёт увеличения шага кадров (детектор измеряет свою
  скорость); на очень длинных видео это снижает точность таймкода до ±1–2 с.

## Проверка устойчивости

Скрипт `scripts/make_augmented.py` создаёт зеркальные (hflip), повёрнутые на ±10° и уменьшенные до
480 px копии; `scripts/eval_all.sh` прогоняет оценку по всем вариантам. Прогон v2.13 (17.10.2026,
детекции и правила на CPU, те же пороги, что и в сервисе):

| набор | recall | ложные на чистых | таймкод ±3 с / ±5 с | тип совпал |
|---|---|---|---|---|
| оригинал (42) | 18/22 = 0.82 | 1/20 (X-14) | 0.72 / 0.89 | 0.78 |
| зеркальные hflip (42) | 12/22 = 0.55 | 1/20 (X-14) | 0.50 / 0.67 | 0.75 |
| уменьшенные 480 px (42) | 16/22 = 0.73 | 2/20 (X-14, X-43) | 0.56 / 0.69 | 0.69 |

Выводы. Ложных срабатываний при смене ракурса/разрешения почти не прибавляется: три поправки по
итогам зеркального прогона (стакан на столе ≥3 с вместо 1.5 с; для «двух посетителей» T4 считаются
только люди у стола, а не у двери; окно «нет клиента» перед входом следующего для T1-B 1 с) сняли
пять из шести ложных на hflip без потерь на оригинале. Пропуски на зеркале растут в основном из-за
модулей, зависящих от стороны сцены (вход/выход через дверь, сторона кассира), — на тестовом видео
с другим ракурсом это главный риск. На уменьшенных копиях теряются мелкие предметы (стакан X-46,
пачка X-4). Таймкоды на вариантах хуже, потому что часть вердиктов там даёт не то правило.
